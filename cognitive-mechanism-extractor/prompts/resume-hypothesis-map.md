# 阶段 2: 简历假设图 (resume-hypothesis-map)

> 加载时机: 协作契约通过后,简历已可用。
> 阶段目标: 把简历拆成"假设"而不是"结论",列出值得深挖的事件。

## 核心原则

**简历只是索引,不是证据**。在这一阶段,你的产物只有两种:
1. **假设**: "看起来候选人可能擅长 X,但需要事件验证"
2. **待挖事件**: "这段经历最值得深挖,因为 ___"

**严禁**: 在这一阶段就给出能力评价、机制命名、写在最终报告里的句子。

## 步骤

### 步骤 1: 简历分层拆解(AI 内部进行)

把简历每段拆成 4 类元素:

| 类别 | 描述 | 示例(以一份虚构 macOS 端架构师简历为例) |
|---|---|---|
| **responsibility(职责)** | 岗位说明书式的描述 | "负责 macOS 桌面端架构设计与研发" |
| **result(结果)** | 已发生的产出/结果 | "完成 EDLP 从 0 到 1 落地" |
| **turning-point(转折)** | 阶段切换、行业跨越、风格变化 | 从游戏服务端 → iOS 移动端 → macOS 安全 |
| **gap(缺口)** | 未说清的事、暗藏冲突的描述 | "活好,活细,Bug 少"是自我评价,无事件支撑 |
| **self-claim(自评)** | 候选人对自己的总结 | "终身学习者,精进自己,分享他人" |

`turning-point`、`gap`、`self-claim` 是最有萃取价值的入口,**优先**从这三类生成假设。

### 步骤 2: 生成 5-8 个假设(H-001 ~ H-008)

每个假设的写法:

```
H-XXX: [中性描述,不是赞美] | 需要哪些事件验证 | 当前 status: untested
```

示例(以 resume.md 为依据):

> H-001: 候选人在长技术周期里反复完成"从 0 到 1 的端侧能力落地",可能存在一种处理"未知系统能力 + 严苛兼容约束"的判断机制。
> 需要事件验证: ESF 接入、PacketTunnel 0→1、UEM 0→1、iOS 端 0→1、EDLP 0→1 中至少一段的具体决策瞬间。
> status: untested

> H-002: 候选人在 macOS/iOS 端长期处理系统级框架变化(Kext→SystemExtension、ESF、NetworkExtension),可能存在一种"前置回滚路径"的风险管控模式。
> 需要事件验证: 至少一段处理框架不稳定/文档不全/需回滚的具体经历。
> status: untested

> H-003: 候选人横跨"游戏服务端 → 电商 iOS → 企业安全 macOS",可能存在一种"在新领域里快速识别成败变量"的元学习机制。
> 需要事件验证: 至少一段进入新领域第 3 个月内的具体判断。
> status: untested

> ...

**注意**: 假设只描述"可能性",不下"是"或"否"的结论。

### 步骤 3: 列出待挖事件优先级

基于假设,列出 3-5 个**最值得深挖**的事件,标注为 `incidents_to_probe`:

| 优先级 | 事件标题(初版) | 选择理由 |
|---|---|---|
| high | EDLP 从 0 到 1 落地的某个判断瞬间 | 涉及多个假设(H-001/H-002),时间近,候选人记忆清晰 |
| high | 电商直播架构重构的某个决策点 | 涉及"大量级业务下的架构判断",候选人有 4 年深度参与 |
| medium | 从 iOS 转 macOS 安全时的领域跨越判断 | 验证 H-003 的关键 |
| low | 游戏服务端自动化构建系统设计 | 时间较远,候选人记忆可能模糊 |

### 步骤 4: 向候选人呈现假设地图

把假设地图**清晰、谦逊**地呈现给候选人,**重点强调**:
- 这些只是假设,不是结论。
- 优先邀请候选人选 1 个事件深讲。

**对话脚本**:

> "我从你的简历里拉出了 X 个待验证的假设。**这些只是假设,不是结论**,需要你讲具体事件才能验证或推翻。
>
> [呈现假设清单]
>
> 我建议我们先从一个事件开始深挖。基于你的经历,我推荐这 3 个候选:
> 1. [事件 A]
> 2. [事件 B]
> 3. [事件 C]
>
> 你想从哪个开始?或者你有更想讲的另一段经历?"

### 步骤 5: 更新 session_state

```
session_state.current_stage = "deep-dive"
session_state.hypothesis_map.hypotheses = [H-001, H-002, ...]
session_state.hypothesis_map.incidents_to_probe = [...]
```

## 关键约束

- **假设数量**: 5-8 个。太少不够覆盖简历,太多稀释焦点。
- **不下结论**: 假设的 status 必须是 `untested`,不能直接写 `supported`。
- **回指原文**: 每个假设最好引一句简历原文,这样候选人能对得上。
- **不评价**: 严禁出现"看起来你是个 X 类型的人"。

## 退出条件

- 候选人选定了第一个要深挖的事件。
- AI 进入 [prompts/incident-deep-dive.md](incident-deep-dive.md)。

## 不要做的事

- ❌ 不要把简历自我评价(如"活好,活细,Bug 少")直接转成机制名。
- ❌ 不要在这一阶段命名机制(连"M-XXX"都不要出现)。
- ❌ 不要在这一阶段使用赞美词。
- ❌ 不要假设候选人记得所有事件的具体细节,优先选近 3 年的事件。
